# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Project

`FX OVERDOSE` — a Unity 6 (6000.5.3f1, URP 2D) Korean-language game. Two single-player halves share one save file, and a third multiplayer part reuses the trading screen:

- **Trading part** (`GameScene`): a real-time leverage-trading sim with a simulated market, HP/mental vitals, boss traders, items/shop, choice events, achievements. Uses an on-device local LLM (LLMUnity + Bllossom 3B GGUF) for choice-event text and the daily diary.
- **DatingSim part** (Phase 2, `YomiRoom` / `WorldMap`): slot-based (non-realtime) dating loop with the character 요미. Its LLM free-chat system was **removed on 2026-08-12**; dialogue now goes through a placeholder provider awaiting a replacement design.
- **P2P multiplayer part** (`Assets/Scripts/P2P/`, added 2026-08-14): Steam-lobby trading competition that keeps the existing `GameScene` visuals and swaps only input and displayed data for authoritative network state. Does **not** use the save file. See the assembly note below — its `Core` is engine-free and unit-tested.

All code, comments, docs, and in-game text are Korean. Match that when editing.

## Commands

There is no CI or npm/make layer. Unity Editor is the primary surface.

**Fast compile check** (~20s, catches all C# errors without opening Unity):
```
dotnet build "Assembly-CSharp.csproj" -v:m             # runtime scripts
dotnet build "Assembly-CSharp-Editor.csproj" -v:m      # editor scripts
dotnet build "FXOverdose.P2P.Core.csproj" -v:m         # P2P core (separate assembly)
dotnet build "FXOverdose.P2P.Core.Tests.csproj" -v:m   # P2P tests
```
**Building only the first two misses the P2P assemblies** — they are separate (see Assembly & namespaces). These `.csproj` files are gitignored and regenerated by Unity; if a newly added `.cs` file isn't picked up, the csproj is stale — reopen Unity or re-run the IDE package's project regeneration.

**Editor / play**: open the project in Unity Hub (`6000.5.3f1` installed at `C:\Program Files\Unity\Hub\Editor\`). Build scenes in order: `TitleScene` → `LoadingScene` → `GameScene` → `tutorial`. `Assets/Scenes/DatingSim/YomiRoom_Test.unity` is **not** in build settings — it is regenerated from scratch by the menu item below.

**Headless build**:
```
"C:\Program Files\Unity\Hub\Editor\6000.5.3f1\Editor\Unity.exe" -quit -batchmode -projectPath "d:\Project\fx overdose" -buildWindows64Player "build\fxoverdose.exe" -logFile -
```

**Tests**: `Assets/Tests/EditMode/` holds **11 EditMode test files** covering the P2P core only (trade calculator/validator, elimination, leaderboard, market sync, connection approval, Steam lobby rules, security guard). Everything outside `FXOverdose.P2P.Core` is untested.

Run them from Unity: **Window → General → Test Runner → EditMode**. `dotnet test` does **not** work — it builds the assembly and reports success without discovering a single test, because the Unity-generated csproj has no VSTest adapter. Use `dotnet build` on the test csproj for a compile check only.

The other automated check is the editor menu `FXOverdose/Debug/AI Trading System Integration Test` (`Assets/Editor/AITradingSystemTestRunner.cs`), run from a loaded scene.

## Editor menu tooling (important)

Much of this project's UI and content is **generated by editor scripts, not hand-authored prefabs**. `Assets/Editor/` holds ~35 `[MenuItem]` builders/stylers/installers. Before hand-editing a scene or prefab, check whether a builder owns it — otherwise your changes get overwritten on the next run. Key ones:

- `FX Overdose/Build Title Screen`, `Build Loading Screen`, `Build YomiRoom Test Scene`, `Build Trading Chart UI`, `Build Comic UI Canvas` — construct whole scenes/canvases.
- `Tools/FX OVERDOSE/Style *` and `Install *` — restyle or inject panels into the current scene.
- `FX Overdose/AI/Import Scenario (CSV+TXT)` — bakes the scenario database (see below).
- `FX Overdose/AI/Clear DatingSim Memory Residue`, `Tools/FX Overdose/Clear All Save Data & Achievements` — wipe `persistentDataPath` state. (The first only clears leftovers from the removed free-chat system.)
- `Tools/Prebake All Scripts Text into Font` — the Korean TMP font atlases are **dynamically prebaked from literal strings in the .cs sources**. Adding new Korean UI strings can require re-running this or characters render as □.

## Architecture

### Assembly & namespaces
Most code compiles into `Assembly-CSharp` / `Assembly-CSharp-Editor`. **Two `.asmdef` files exist** (both from the P2P work, 2026-08-14):

| asmdef | Covers | Note |
| --- | --- | --- |
| `Assets/Scripts/P2P/Core/FXOverdose.P2P.Core.asmdef` | 17 files — match rules, trade calc/validation, elimination, leaderboard, Steam lobby models | `noEngineReferences: true` and **zero references**: pure C#, no `UnityEngine`. That is what makes it unit-testable. **Do not add a Unity type to it.** |
| `Assets/Tests/EditMode/FXOverdose.P2P.Core.Tests.asmdef` | 11 EditMode test files | Tests the above |

`Assets/Scripts/P2P/Infrastructure/` (Netcode/Steamworks glue) and `Assets/Scripts/P2P/UI/` have **no** asmdef — they compile into `Assembly-CSharp` like everything else, so they can reach `GameManager`, `TraderStatus`, and the existing UI controllers.

Newer code lives under `FXOverdose.*` namespaces; the oldest core types (`GameManager`, `TraderStatus`, `Inventory`, `HUDController`, items) are in the **global namespace**, so cross-references need `using FXOverdose.X` one way and nothing the other.

### Manager pattern
Nearly every system is a `MonoBehaviour` singleton exposing `public static X Instance`. Some are scene-scoped (`ScenarioManager`, `YomiRoomManager`), some `DontDestroyOnLoad` (`SaveLoadManager`, `ScenarioExampleManager`). Some are found by `FindAnyObjectByType` instead (`GameManager`, `TradingController` in save code).

`TraderStatus` is the exception worth knowing: multiple instances can exist across scenes, and `TraderStatus.CanonicalInstance` (the one on the `GameManager` object) is authoritative — non-canonical copies mirror it via `SyncFromCanonical()`. Never assume `GetComponent<TraderStatus>()` gave you the real one.

### Layering convention
Managers hold logic and data and expose `event Action<...>`; UI controllers subscribe and never own state. This is applied consistently in the Phase 2 DatingSim code and partially in the trading code. Follow it for new work — a manager must not reference a UI controller.

### Save data
`SaveLoadManager` writes `Application.persistentDataPath/save_slot_{0..2}.json` via `JsonUtility`. Saving is only allowed in `GameMode.Story`. Save is a wide gather across many singletons in `SaveGame()`; **adding persisted state means touching `SaveData`, the gather in `SaveGame()`, and the scatter in the load path**. `SaveDataMigrator.Migrate()` runs a version-comparison pipeline on load — add backfill logic there when changing `SaveData` shape.

### Trading loop
`GameManager` owns the clock (`secondsPerGameMinute`, `OnGameMinuteAdvanced`, `OnDayEnded`), balance (`ChangeBalance` / `TrySpendBalance`), story events and endings. `MarketSimulationEngine` generates price/candles and emits `OnPriceUpdated`/`OnCandleClosed`/`OnMarketSignalGenerated`; `TradingController` consumes them for position lifecycle; `ChartUIController`/`TradingPanelUIController` render. `AITradingBrain` + `BossManager` drive the rival AI. `DynamicTimeRegulator` applies slow-motion/timescale effects.

Several of these files are very large (`TradingController.cs` ~88KB, `TradingPanelUIController.cs` ~74KB, `MarketSimulationEngine.cs` ~69KB). Grep for the region/method before reading whole files.

### DatingSim dialogue (자유 채팅 LLM 제거됨 — 2026-08-12)
The local-LLM free-chat system was removed from the DatingSim half. The removal record is [DatingSim_FreeChat_Removal_Plan.md](docs/P2_03_LLM_Architecture/DatingSim_FreeChat_Removal_Plan.md); the superseded design docs sit in `docs/P2_03_LLM_Architecture/_Deprecated/` and **do not describe current code**.

What remains:
- **The chat UI is fully intact** — panel, input field, send button, bubble log, the `자유대화` button. Only response generation was cut. Do not delete these.
- Responses now come from `FXOverdose.DatingSim.Dialogue.IYomiDialogueProvider` (`Assets/Scripts/DatingSim/Dialogue/`). The only implementation is `PlaceholderDialogueProvider`, which returns one fixed "준비 중" line and reports `IsAvailable == false`. A replacement dialogue system plugs in by swapping this implementation — `YomiRoomManager.SetDialogueProvider()` and the field in `YomiRoomDialogueUI` are the two injection points.
- `YomiRoomState` is `Idle` / `Chatting` / `Responding` / `Resting` / `Transitioning`. Chat currently consumes **no** time slot and grants **no** affection (both marked `TODO(P2)` — deliberate, so a placeholder reply can't be farmed).
- `FXOverdose.DatingSim.Scenario` (`Assets/Scripts/DatingSim/Scenario/`) survived the removal because its matching logic never depended on the LLM, but **nothing calls it** — `StartNewScenario`/`IncrementTurn` have no callers. Its zero-allocation constraint (`for` loops only, no LINQ, in `ScenarioMatcher`) still applies if it gets rewired.

The **trading** half still uses a local LLM: `LLMSafeGenerator` (`Assets/Scripts/AI/LLM/`) generates choice-event text and the daily diary, hosted on the `LLM_Manager` object in `TitleScene` (`DontDestroyOnLoad`) and backed by the **Bllossom 3B** model — not the 7B. Leave it alone.

`WorldMapManager` links the two halves' economy by calling `GameManager.ChangeBalance` / `TrySpendBalance` directly for part-time-job rewards and date costs.

### Scenario authoring pipeline (currently dormant)
Dual-track by design so writers don't work in spreadsheet cells:
- Numbers/flags: `Assets/Data/Scenarios/ScenarioMaster.csv`
- Prose: `Assets/Data/Scenarios/Story_Scripts/{ScenarioID}.txt`, sectioned `# Context` / `# Goal` / `# Dialogues`
- Baked together by `ScenarioCSVImporter` (`FX Overdose/AI/Import Scenario (CSV+TXT)`) into a `ScenarioDatabase` ScriptableObject. `ScenarioMatcher` gets its database via `[SerializeField]` scene wiring, not `Resources.Load`, so check the inspector reference after re-baking.
- **None of these data files exist yet** — no `Assets/Data/Scenarios/`, no baked `ScenarioDatabase.asset`. The pipeline is code-only scaffolding.

### Scene transitions
Always go through `LoadingScene`. Set the static before loading it:
```csharp
LoadingScreenController.TargetSceneToLoad = "YomiRoomScene";
```
It resets itself once loading starts. Scene load counts as 65% of the bar; `GameScene` and `tutorial` then wait on chart-system readiness before finishing. (The old `RequireLLM` flag and its model-load wait were removed with the free-chat system.)
