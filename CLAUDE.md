# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`FX OVERDOSE` — a Unity 6 (6000.5.3f1, URP 2D) Korean-language game. Two loosely-coupled halves share one save file:

- **Trading part** (`GameScene`): a real-time leverage-trading sim with a simulated market, HP/mental vitals, boss traders, items/shop, choice events, achievements.
- **DatingSim part** (Phase 2, `YomiRoom` / `WorldMap`): slot-based (non-realtime) dating loop with the character 요미, driven by an **on-device local LLM** (LLMUnity + Qwen2.5-7B GGUF).

All code, comments, docs, and in-game text are Korean. Match that when editing.

## Commands

There is no CI, test suite, or npm/make layer. Unity Editor is the primary surface.

**Fast compile check** (~20s, catches all C# errors without opening Unity):
```
dotnet build "Assembly-CSharp.csproj" -v:m          # runtime scripts
dotnet build "Assembly-CSharp-Editor.csproj" -v:m   # editor scripts
```
These `.csproj` files are gitignored and regenerated by Unity; if a newly added `.cs` file isn't picked up, the csproj is stale — reopen Unity or re-run the IDE package's project regeneration.

**Editor / play**: open the project in Unity Hub (`6000.5.3f1` installed at `C:\Program Files\Unity\Hub\Editor\`). Build scenes in order: `TitleScene` → `LoadingScene` → `GameScene` → `tutorial`. `Assets/Scenes/DatingSim/YomiRoom_Test.unity` is **not** in build settings — it is regenerated from scratch by the menu item below.

**Headless build**:
```
"C:\Program Files\Unity\Hub\Editor\6000.5.3f1\Editor\Unity.exe" -quit -batchmode -projectPath "d:\Project\fx overdose" -buildWindows64Player "build\fxoverdose.exe" -logFile -
```

**"Tests"**: `com.unity.test-framework` is installed but there are no test assemblies. The only automated check is the editor menu `FXOverdose/Debug/AI Trading System Integration Test` (`Assets/Editor/AITradingSystemTestRunner.cs`), run from a loaded scene.

## Editor menu tooling (important)

Much of this project's UI and content is **generated by editor scripts, not hand-authored prefabs**. `Assets/Editor/` holds ~35 `[MenuItem]` builders/stylers/installers. Before hand-editing a scene or prefab, check whether a builder owns it — otherwise your changes get overwritten on the next run. Key ones:

- `FX Overdose/Build Title Screen`, `Build Loading Screen`, `Build YomiRoom Test Scene`, `Build Trading Chart UI`, `Build Comic UI Canvas` — construct whole scenes/canvases.
- `Tools/FX OVERDOSE/Style *` and `Install *` — restyle or inject panels into the current scene.
- `FX Overdose/AI/Import Scenario (CSV+TXT)` — bakes the scenario database (see below).
- `FX Overdose/AI/Clear Memory DB (Fix Halucination)`, `Tools/FX Overdose/Clear All Save Data & Achievements` — wipe `persistentDataPath` state.
- `Tools/Prebake All Scripts Text into Font` — the Korean TMP font atlases are **dynamically prebaked from literal strings in the .cs sources**. Adding new Korean UI strings can require re-running this or characters render as □.

## Architecture

### Assembly & namespaces
No `.asmdef` files exist — everything compiles into `Assembly-CSharp` / `Assembly-CSharp-Editor`. Newer code lives under `FXOverdose.*` namespaces; the oldest core types (`GameManager`, `TraderStatus`, `Inventory`, `HUDController`, items) are in the **global namespace**, so cross-references need `using FXOverdose.X` one way and nothing the other.

### Manager pattern
Nearly every system is a `MonoBehaviour` singleton exposing `public static X Instance`. Some are scene-scoped (`ScenarioManager`, `YomiRoomManager`), some `DontDestroyOnLoad` (`SaveLoadManager`, `ScenarioExampleManager`). Some are found by `FindAnyObjectByType` instead (`GameManager`, `TradingController` in save code).

`TraderStatus` is the exception worth knowing: multiple instances can exist across scenes, and `TraderStatus.CanonicalInstance` (the one on the `GameManager` object) is authoritative — non-canonical copies mirror it via `SyncFromCanonical()`. Never assume `GetComponent<TraderStatus>()` gave you the real one.

### Layering convention
Managers hold logic and data and expose `event Action<...>`; UI controllers subscribe and never own state. This is applied consistently in the Phase 2 DatingSim code and partially in the trading code. Follow it for new work — a manager must not reference a UI controller.

### Save data
`SaveLoadManager` writes `Application.persistentDataPath/save_slot_{0..2}.json` via `JsonUtility`. Saving is only allowed in `GameMode.Story`. Save is a wide gather across many singletons in `SaveGame()`; **adding persisted state means touching `SaveData`, the gather in `SaveGame()`, and the scatter in the load path**. `SaveDataMigrator.Migrate()` runs a version-comparison pipeline on load — add backfill logic there when changing `SaveData` shape.

### Trading loop
`GameManager` owns the clock (`secondsPerGameMinute`, `OnGameMinuteAdvanced`, `OnDayEnded`), balance (`ChangeBalance` / `TrySpendBalance`), story events and endings. `MarketSimulationEngine` generates price/candles and emits `OnPriceUpdated`/`OnCandleClosed`/`OnMarketSignalGenerated`; `TradingController` consumes them for position lifecycle; `ChartUIController`/`TradingPanelUIController` render. `AITradingBrain` + `BossManager` drive the rival AI. `DynamicTimeRegulator` applies slow-motion/timescale effects.

Several of these files are very large (`TradingController.cs` ~88KB, `TradingPanelUIController.cs` ~74KB, `MarketSimulationEngine.cs` ~69KB). Grep for the region/method before reading whole files.

### DatingSim + LLM ("대본 연기형" / scenario-driven actor)
This is the most intricate subsystem; the authoritative writeup is [DatingSim_Scenario_Architecture_Manual.md](docs/P2_03_LLM_Architecture/DatingSim_Scenario_Architecture_Manual.md). Flow per conversation turn:

1. `YomiRoomManager` spends a time slot via `DatingTimeManager`, then `ScenarioManager.StartNewScenario(category, timeOfDay)`.
2. `ScenarioMatcher` picks a scene: O(1) `Dictionary` prefilter on `category_timeOfDay` in `ScenarioDatabase`, then scoring against affection/obsession/mood/idle/flags. Top-tier candidates within 5 points are **randomly pooled** to avoid repetition; a cooldown `HashSet` blocks reruns, with a forced-ignore fallback when every candidate is on cooldown.
3. `ScenarioExampleManager.LoadChunkAsync(scenarioID)` streams `Assets/StreamingAssets/ScenarioExamples/{scenarioID}.csv` (**pipe-delimited**, `UserIntent|RequiredMood|RequiredAffection|DialogueText`) into memory, flushed by `UnloadChunk()` when the scene ends.
4. `DatingSimLLMController.ConstructSystemPrompt()` assembles: persona rules + current scene Context/Goal + dynamically matched example lines + affection-tier behavior directive, overwrites `llmAgent.systemPrompt`, and calls `llmAgent.Chat()`.
5. Output goes through `ParseAndValidate()` — first line only, emoji/CJK stripping, a Korean honorific→casual-speech substitution table, and `IsValidKorean()`; anything failing falls back to `dummyDialogues`.
6. `DatingSimMemoryDB` appends both sides to a short-term scene buffer; on scene end (`MaxTurns`) it chunks that into per-topic JSON under `persistentDataPath/DatingSimMemories/`. All I/O is `async`.

Two hard constraints in this subsystem, deliberately chosen: **zero-allocation scoring** (`for` loops only, no LINQ, in `ScenarioMatcher`/`ScenarioExampleManager` — they run every turn) and **no main-thread blocking** (every LLM/file call is `async Task`).

`WorldMapManager` links the two halves' economy by calling `GameManager.ChangeBalance` / `TrySpendBalance` directly for part-time-job rewards and date costs.

### Scenario authoring pipeline
Dual-track by design so writers don't work in spreadsheet cells:
- Numbers/flags: `Assets/Data/Scenarios/ScenarioMaster.csv`
- Prose: `Assets/Data/Scenarios/Story_Scripts/{ScenarioID}.txt`, sectioned `# Context` / `# Goal` / `# Dialogues`
- Baked together by `ScenarioCSVImporter` into a `ScenarioDatabase` ScriptableObject. Note the importer's default output path (`Assets/Resources/ScenarioDatabase.asset`) differs from where the current asset lives (`Assets/Resources/Scenarios/ScenarioDatabase.asset`); `ScenarioMatcher` gets its database via `[SerializeField]` scene wiring, not `Resources.Load`, so check the inspector reference after re-baking.

### Scene transitions
Always go through `LoadingScene`. Set the statics before loading it:
```csharp
LoadingScreenController.TargetSceneToLoad = "YomiRoom_Test";
LoadingScreenController.RequireLLM = true;  // splits the bar 50% scene / 50% model load
```
Both reset themselves once loading starts. With `RequireLLM`, it waits on `DatingSimLLMController.IsLLMReady` so the multi-GB GGUF load happens behind one continuous progress bar. Existing callers (`MainMenuController`, `TutorialManager`) only set `TargetSceneToLoad`; no caller sets `RequireLLM` yet, so the DatingSim entry point still needs wiring.

## Repo conventions

- **Do not read or reference `docs/Phase1_Backup/`** — obsolete Phase 1 material (this rule comes from [.agents/AGENTS.md](.agents/AGENTS.md)). Use `docs/P2_*` for all design/architecture reference.
- `docs/P2_04_System/Refactored_Architecture_Master.md` is the running refactor log — append there when making structural changes.
- Root-level `AIVisualController_dev.cs` / `AIVisualController_old.cs` and the `*.py` scripts (`refactor_visual.py`, `clean_aivisual.py`, `fix_market.py`) are one-off scratch refactoring tools outside `Assets/` — not compiled, not part of the game.
- `.gguf` model files under `Assets/StreamingAssets/Models/` are gitignored (too large); a fresh clone will not have them and the DatingSim part won't run until they're placed there.
