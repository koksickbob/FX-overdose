본 문서는 프로젝트 개발 과정에서 실제로 사용한 요청을 기능별로 분류하고, 구어체·축약어·오탈자·반복 피드백을 제거하여 공식적인 프롬프트 형태로 재구성한 자료이다. 따라서 대화 원문을 그대로 전사한 문서가 아니라, 원문의 목적과 제약 조건을 유지한 정제본이다.

2. 공통 프로젝트 컨텍스트

아래 내용은 개별 요청에 반복적으로 적용한 공통 조건이다.

Unity 2D 기반 모바일 가로형 게임인 「FX OVERDOSE」를 개발한다.
게임은 비트코인 선물 트레이딩, 경영 시뮬레이션, 감정형 AI 캐릭터 육성을 결합한 장르이다.

기존 기획서와 구현 코드를 먼저 검토하고, 이미 동작하는 기능과 팀원의 변경 사항을 보존한다.
UI는 1920×1080 기준의 픽셀 아트 스타일로 제작하며, 네이비·시안 계열의 기존 색상 팔레트와 PF Stardust 폰트를 사용한다.
모바일 화면에서 요소가 겹치거나 잘리지 않도록 앵커, 여백, 종횡비와 외곽선 두께를 일관되게 유지한다.
동적으로 생성되는 아이템과 UI를 고려하고, 단순한 정적 시안에 그치지 않도록 기존 게임 로직과 실제로 연동한다.
작업 완료 후 Unity 컴파일과 주요 플레이 흐름을 확인하고, 구현 내용을 개발 기록 문서에 추가한다.

3. 기획 및 초기 구조 프롬프트

P-01. 기획 문서 분석 및 개발 순서 수립

활용 목적: 기획 의도 파악과 우선순위 설정

docs 폴더의 상세 기획서와 관련 시스템 문서를 검토하라.
현재 프로젝트에 구현된 기능과 미구현 기능을 구분하고, 팀원이 담당하는 모의 차트 작업과 독립적으로 진행할 수 있는 개발 항목을 우선순위 순으로 제안하라.
각 단계는 초보 개발자도 따라갈 수 있도록 필요한 Unity 설정, 코드, 연결 방법과 확인 절차를 포함하라.

P-02. 모바일 화면 및 Canvas 기준 설정

활용 목적: 모바일 해상도 대응 기반 마련

현재 GameScene을 모바일 가로 화면에 맞게 구성하라.
Canvas Scaler는 1920×1080 기준 해상도를 사용하고, 화면 비율이 달라져도 HUD와 배경이 안정적으로 배치되도록 앵커와 Match 값을 설정하라.
배경 이미지는 화면 전체에 표시하되 종횡비가 찌그러지지 않게 하고, 이후 추가될 UI가 Safe Area를 침범하지 않도록 기준 여백을 정의하라.

P-03. 게임 진행 및 캐릭터 상태 시스템

활용 목적: 핵심 게임 루프의 기반 구현

게임 상태, 날짜와 시간, 자산, 성공·파산·Overdose 엔딩을 관리하는 GameManager를 구현하라.
별도의 TraderStatus에서 체력과 멘탈을 관리하고, 게임 진행 시간에 따라 수치가 자동으로 감소하도록 연결하라.
멘탈 수치에 따라 Stable, Anxious, Danger, Overdose 상태를 구분하고, 멘탈이 0이 되면 게임오버 로직과 연동하라.
코드에는 역할과 동작을 이해할 수 있는 한국어 주석을 포함하라.

4. 메인 게임 UI/UX 프롬프트

P-04. 상단 상태 HUD 통합

활용 목적: 핵심 정보를 일관된 시각 체계로 제공

화면 상단에 DAY·TIME, BALANCE, P&L, HP, MENTAL과 설정 버튼을 한 줄로 배치하라.
모든 카드는 동일한 배경 스타일, 높이, 상하 여백과 외곽선 두께를 사용한다.
HP와 MENTAL은 중앙 구분선을 기준으로 좌우 여백을 대칭으로 맞추고, 게이지가 배경 프레임을 침범하지 않도록 내부 마진을 둔다.
P&L 그래프와 긴 수치가 카드 밖으로 나오지 않도록 마스크와 자동 축소 범위를 적용하라.

P-05. 트레이딩 차트 UI

활용 목적: 실제 거래 화면과 유사한 차트 정보 구조 구현

BTC/USDT 종목명, 현재가, 등락률, 시간 간격 버튼, 캔들 차트, 거래량, 시간축과 가격축을 포함한 트레이딩 차트 UI를 제작하라.
가격축과 현재가 태그는 차트 프레임 내부에 배치하고, 캔들 영역이 가격축 바로 옆까지 확장되도록 불필요한 공백을 제거하라.
텍스트와 캔들이 헤더 또는 프레임 밖으로 나오지 않도록 플롯 영역과 클리핑 범위를 분리하라.
기존 차트 시뮬레이션 데이터와 갱신 메서드는 유지한다.

P-06. 롱·숏·청산 및 레버리지·마진 조작부

활용 목적: 매매 조작의 명확성 및 모바일 조작성 개선

차트 하단에 LONG, SHORT와 레버리지·마진 조작부를 배치하고 차트 좌우선과 동일한 여백으로 정렬하라.
포지션이 없을 때는 LONG과 SHORT 버튼을 표시하고, 포지션 진입 후에는 두 버튼 영역을 합친 크기의 청산 버튼을 표시하라.
레버리지와 마진은 탭으로 전환할 수 있게 하며, 증감 버튼·현재 값·단계 버튼의 상하 간격을 동일하게 맞춰 중앙 정렬하라.
AI가 포지션을 진입한 경우에도 동적 상태 텍스트가 화면 밖으로 밀리지 않도록 자동 크기 조절과 내부 여백을 적용하라.

P-07. 매매 모드·레벨·스킬 HUD

활용 목적: 보조 기능의 배치 및 상호작용 통합

AUTO/USER 전환 버튼을 차트 오른쪽, P&L 카드 아래에 배치하고 다른 UI 영역과 겹치지 않도록 한다.
캐릭터 레벨과 EXP UI는 전환 버튼 오른쪽에 같은 높이로 배치하며, 외곽선 두께를 차트와 버튼 UI에 맞춘다.
설정 버튼 아래에는 액티브 스킬 3개를 세로로 각각 분리하여 정렬하고, 버튼 사이에 동일한 간격을 둔다.
스킬 버튼을 누르면 상세 정보와 현재 레벨, 다음 효과, 비용, 실제 업그레이드 버튼이 포함된 팝업을 표시하고 기존 스킬 시스템과 연동하라.

P-08. PF Stardust 폰트 안정화

활용 목적: 작은 HUD 텍스트의 글리프 깨짐 방지

게임에서 사용하는 TMP 텍스트를 PF Stardust 폰트로 통일하라.
특히 AUTO/USER, LV, EXP와 숫자가 작은 영역에서 뭉개지거나 간헐적으로 깨지지 않도록 글리프를 사전 준비하고, 잘못된 Auto Size 범위와 중복 Bold·Outline을 제거하라.
전역 폰트 적용 코드가 개별 텍스트의 머티리얼과 외곽선 설정을 덮어쓰지 않도록 수정하라.
에디터에서만 정상적으로 보이는지에 그치지 말고 빌드 환경의 동적 아틀라스 초기화도 고려하라.

5. 아이템·인벤토리·상점 프롬프트

P-09. 회복 아이템과 인벤토리 기반 구현

활용 목적: 캐릭터 케어 루프 구축

ScriptableObject 기반 ItemData를 만들고 에너지 드링크, 디저트, 영양제와 진정제를 구현하라.
아이템마다 ID, 이름, 설명, 가격, 아이콘, 체력·멘탈 회복 효과를 정의한다.
Inventory는 슬롯 개수와 아이템 보유량을 관리하고, 실제 사용에 성공한 경우에만 수량을 차감한다.
능력치가 최대이거나 보유 수량이 0인 경우 사용을 차단하고 UI를 즉시 갱신하라.

P-10. 동적 인벤토리 UI

활용 목적: 아이템 추가·삭제에 대응하는 확장형 UI 구현

픽셀 아트 기반 CARE ITEMS 인벤토리 패널을 제작하라.
Inventory의 슬롯 수와 실제 등록 아이템 개수에 맞춰 슬롯 UI를 동적으로 생성·정렬하고, 아이템 추가 또는 삭제 시 별도의 씬 재작업 없이 자동 반영되도록 한다.
아이콘은 슬롯의 정중앙에 위치시키고 모든 방향의 시각적 여백을 동일하게 유지한다.
아이템 수량은 아이콘 위에 겹치지 않도록 우측 하단에 명확히 표시하라.

P-11. 인터넷 쇼핑몰형 상점

활용 목적: 구매 경험과 상품 확장성 개선

기존 상점 UI를 쿠팡 또는 아마존과 같은 인터넷 쇼핑몰 구조를 참고한 FX MARKET 형태로 개편하라.
검색창, 카테고리 탭, 잔액, 상품 카드, 보유 수량, 가격과 구매 버튼을 제공하되 게임의 네이비·시안 픽셀 UI와 조화를 이루게 한다.
CARE ITEM, ACTIVE GEAR와 APPAREL 상품을 데이터 개수에 따라 동적으로 생성하고, 아이템 추가·삭제·검색·필터링에 즉시 대응하게 한다.
구매 후 자산과 인벤토리 보유량을 같은 프레임에서 갱신하고, OWNED 표기와 BUY 버튼이 카드 경계에서 잘리지 않도록 안전 여백을 적용하라.

P-12. 아이템 사용 캐릭터 연출

활용 목적: 아이템 사용에 대한 시각적 피드백 제공

에너지 드링크, 디저트, 영양제와 진정제 사용 시 각각의 행동이 드러나는 캐릭터 스프라이트를 제작하라.
예를 들어 에너지 드링크는 캐릭터가 캔 음료를 마시는 포즈로 표현한다.
스프라이트는 기존 캐릭터와 동일한 캔버스, 중심 좌표와 비율을 사용하고 투명 배경으로 제작한다.
아이템 소비가 성공한 경우에만 약 1초간 표시하고, 이후 가장 최근의 감정 스프라이트로 복귀하도록 연동하라.

6. 캐릭터 및 이미지 에셋 프롬프트

P-13. 기본 캐릭터 스프라이트 교체와 누끼 보정

활용 목적: 캐릭터 품질 및 일관성 향상

제공한 캐릭터 이미지를 기준으로 현재 게임 캐릭터 스프라이트를 교체하라.
초록 크로마키 배경과 반투명 녹색 외곽 잔상을 완전히 제거하고, 투명 픽셀의 숨은 RGB까지 정리한다.
기존 UI 구도에 맞춰 캐릭터의 중심, 발끝과 표시 크기를 유지하고 Point 필터와 무압축 설정으로 픽셀 선명도를 보존하라.
원본 이미지와 Unity 표시 결과의 종횡비가 달라지지 않도록 한다.

P-14. 19종 감정 스프라이트 제작 및 연동

활용 목적: 게임 상태에 따른 캐릭터 감정 표현 확장

현재 기본 캐릭터 스프라이트의 얼굴, 의상, 신체 비율과 착석 구도를 기준으로 TraderEmotion 19종의 감정 스프라이트를 제작하라.
Euphoria, Confident, Pleased, Relieved, Affectionate, Focused, Suspicious, Anxious, Frustrated, Regretful, Jealous, Panicked, Despairing, Furious, Tearful, Manic, Obsessive, Exhausted와 Vengeful을 각각 시각적으로 구분한다.
모든 결과물은 동일한 캔버스 크기와 중심 좌표, 투명 배경을 사용한다.
ROE, 멘탈, 체력과 이벤트 상태를 판정하는 기존 메서드를 확인하여 각 감정을 런타임 스프라이트와 연결하라.

P-15. 코스튬 변형 스프라이트

활용 목적: 캐릭터 정체성을 유지한 의상 콘텐츠 확장

기존 요미의 얼굴, 눈과 피부색, 체형, 포즈, 표정, 손·다리 배치, 소품과 화면 구도를 유지하고 의상과 필요한 머리 장식만 지정된 코스튬으로 변경하라.
기본 상태, 19종 감정, 아이템 사용, 롱·숏 포지션, 스킬 강화와 Overdose 상태를 동일한 디자인 규칙으로 일괄 제작한다.
포즈나 해부학적 비율이 변하거나 손·발·소품이 잘리지 않도록 원본 상태 이미지를 동작 기준으로 사용한다.
승인 전에는 실제 Resources 경로와 기존 meta 파일을 변경하지 말고 별도의 검수 폴더에 결과를 제공하라.

P-16. 캐릭터 말풍선과 대사 레이아웃

활용 목적: 긴 대사의 가독성 및 정렬 개선

캐릭터 왼쪽, 말풍선 오른쪽 구도를 유지하며 말풍선 프레임을 고해상도 픽셀 UI로 교체하라.
배경과 외곽선은 UI 디자인 가이드의 색상 코드를 사용하고, 불필요한 하단 화살표 이미지는 제거한다.
대사 텍스트에는 PF Stardust를 적용하고 프레임 내부의 상하좌우 여백을 시각적으로 동일하게 맞춘다.
긴 문장은 자동 줄바꿈하고 말풍선 밖으로 넘치지 않도록 하며, 텍스트 블록이 실제 프레임 본체 중앙에 위치하도록 꼬리 영역을 제외해 보정하라.

7. 화면 전환 및 게임 흐름 프롬프트

P-17. 타이틀 및 로딩 화면

활용 목적: 게임 진입 흐름 완성

타이틀·로딩 화면 조립 가이드를 기준으로 TitleScene과 LoadingScene을 제작하라.
타이틀에는 NEW GAME, CONTINUE, SETTINGS와 QUIT 버튼을 제공하고 저장 슬롯 및 설정 팝업을 기존 시스템과 연결한다.
로딩 화면은 검은 배경, 중앙의 잠자는 SD 캐릭터, 하단 0~100% 진행 바를 사용한다.
LLM과 차트 준비 상태가 모두 완료된 경우에만 100%가 되게 하고, 페이드 아웃 후 0.5초 동안 게임을 정지한 다음 첫 대사와 게임 진행을 시작하라.
모든 씬에 유효한 카메라가 존재하도록 하여 No cameras rendering 상태를 방지하라.

P-18. 3종 게임 모드와 저장 슬롯

활용 목적: 플레이 방식 분리 및 세이브 정책 정의

게임 모드를 STORY, ENDLESS와 CHALLENGE의 세 가지로 구분하라.
STORY를 선택한 경우에만 기존 3개 저장 슬롯을 선택하여 새 게임 또는 이어하기가 가능하도록 한다.
ENDLESS는 AI 자동매매를 허용하되 저장을 제한하고, CHALLENGE는 AI 자동매매와 우회 강제 진입을 금지하여 USER 수동매매로 고정한다.
기존 저장 파일은 Story 모드로 안전하게 호환하고, 현재 모드를 설정 및 저장 UI에 명확히 표시하라.

P-19. 시간대별 배경 전환

활용 목적: 게임 시간의 시각적 체감 강화

기존 밤 트레이딩 룸을 기준으로 같은 구도와 픽셀 스타일의 아침 및 해질녘 배경을 제작하라.
게임 시각 06:00~16:59에는 아침, 17:00~19:59에는 해질녘, 20:00~05:59에는 밤 배경을 표시한다.
시간대가 바뀔 때 0.8초 크로스페이드를 적용하고, 일시정지·세이브 불러오기·다음 날 전환처럼 시간이 즉시 변경되는 경우에도 올바른 배경을 표시하라.
기존 배경의 위치와 UI 정렬 순서는 변경하지 않는다.

8. 이벤트·정산·게임오버 프롬프트

P-20. 인터넷 기사형 돌발 이벤트

활용 목적: 선택 이벤트의 정보 전달력과 몰입도 향상

현재 돌발 이벤트 UI를 인터넷 뉴스 기사 형태로 개편하라.
브라우저 주소 표시줄, 뉴스 사이트 헤더, BREAKING NEWS 티커, 기사 제목·본문·출처와 선택지를 구성하되 기존 게임 UI 팔레트와 픽셀 스타일을 유지한다.
본문은 독립적으로 스크롤하고 선택지는 RESPONSE DESK에 고정하여 긴 기사에서도 항상 조작할 수 있게 한다.
팝업은 다른 HUD보다 높은 정렬 순서를 사용하고, 필요 아이템 수량·선택 가능 여부·게임 일시정지와 기존 이벤트 효과를 그대로 연동하라.

P-21. 일일 정산 UI

활용 목적: 하루 단위 성과 요약 및 다음 날 전환

일일정산 UI 설계서를 기준으로 24:00에 자동으로 열리는 DAILY LEDGER 화면을 구현하라.
당일 순자산 손익, 수익률, 시작·현재 자산, HP와 멘탈 상태를 표시하고 수익·손실·보합을 색상과 아이콘으로 구분한다.
정산 결과에 맞는 캐릭터 감정과 반응 대사를 표시하며, 다음 날 버튼을 누르면 수면 페이드 연출 후 다음 날 09:00부터 게임을 재개한다.
열린 포지션, 저장 데이터, 비동기 대사 지연과 중복 정산을 안전하게 처리하라.

P-22. 게임오버 최종 리포트

활용 목적: 플레이 결과와 엔딩 정보 제공

게임오버 UI 가이드를 기준으로 파산, Overdose와 성공 엔딩에 대응하는 최종 세션 리포트를 구현하라.
종료 사유, 엔딩 코드, 최종 자산, 플레이 일수, 캐릭터 상태와 적절한 감정 스프라이트를 표시한다.
게임오버 중에는 다른 UI 입력을 차단하고, RETURN TO TITLE 버튼을 누르면 페이드 아웃 후 Time Scale과 대기 중인 대사를 정리한 뒤 TitleScene으로 이동하라.

9. AI 및 대사 시스템 프롬프트

P-23. 온디바이스 LLM 연결

활용 목적: 네트워크 없이 캐릭터 대사 생성

현재 프로젝트에서 제거되거나 연결이 끊긴 AI 런타임을 확인하고, Qwen 3 3B INT4급 온디바이스 모델을 프로젝트에 연결하라.
모델은 모바일 메모리와 로딩 시간을 고려하여 준비하고, Unity 메인 스레드를 차단하지 않는 비동기 추론 인터페이스를 제공한다.
로딩 화면의 0~100% 진행률과 모델 준비 상태를 연동하고, 초기화 실패 시 게임이 멈추지 않도록 폴백 대사를 제공하라.
대용량 모델 파일은 저장소 정책과 배포 방식을 별도로 문서화하라.

P-24. 감정·상황 기반 대사 출력

활용 목적: 매매 상황에 맞는 캐릭터 반응 생성

캐릭터 대사는 현재 포지션, 시장 추세, 수익률, 멘탈 상태, 체력과 이벤트 문맥을 반영하도록 구성하라.
일반적인 매매 반응은 빠르고 안정적인 규칙 기반 또는 데이터셋 매칭 방식으로 처리하고, 돌발 이벤트와 일일 정산처럼 서사성이 필요한 영역에만 LLM을 사용한다.
같은 대사가 반복되지 않도록 쿨다운과 최근 출력 이력을 관리하고, 생성 실패 또는 데이터베이스 미연결 시 실제 캐릭터 말투의 폴백 문장을 출력하라.
프롬프트 지시문이나 내부 상태 설명이 사용자 말풍선에 그대로 노출되지 않도록 분리하라.

10. 튜토리얼 및 확장 콘텐츠 프롬프트

P-25. 단계형 튜토리얼과 UI 하이라이트

활용 목적: 초보 사용자의 게임 조작 학습 지원

타이틀에서 튜토리얼을 선택하면 전용 씬을 로드하고, 캐릭터 대사와 단계별 UI 하이라이트로 게임 조작을 안내하라.
잔고, 증거금, 레버리지, 멘탈, 상점, 레벨·EXP, 롱·숏 버튼 등 현재 설명 중인 요소만 정확히 강조한다.
하이라이트는 최상단 Canvas에서 실제 대상의 화면 좌표를 추적하고, Canvas Scaler·Layout Group·Additive Scene 로딩에도 위치가 어긋나지 않게 한다.
조작이 필요한 단계에서는 투명 입력 차단막이 해당 버튼 클릭을 가로채지 않도록 처리하고, 완료 후 START TRADING 화면을 제공하라.

P-26. 오디오·업적·코스튬 확장

활용 목적: 반복 플레이 콘텐츠와 완성도 향상

기존 데이터와 UI 구조를 유지하면서 BGM·SFX 오디오 시스템, 전역 업적과 코스튬 구매·장착 기능을 추가하라.
오디오는 씬 전환 후에도 설정값을 유지하고, 설정 팝업의 볼륨 슬라이더와 연결한다.
업적 달성 조건과 진행률을 UI에 표시하고, 특정 업적이 코스튬 잠금 해제 조건으로 작동하게 한다.
상점 APPAREL 카테고리는 코스튬 추가·삭제를 자동 반영하며, 장착 즉시 감정·아이템·포지션·스킬 상태 스프라이트 전체에 같은 의상이 적용되도록 한다.

11. 오류 수정 및 반복 개선 프롬프트

P-27. UI 배치 오류 진단

활용 목적: 겹침·잘림·비율 문제의 근본 원인 수정

첨부한 게임 화면을 기준으로 UI가 프레임 밖으로 나오거나 다른 요소와 겹치는 원인을 확인하라.
단순히 좌표만 임의 변경하지 말고 Anchor, Pivot, Layout Group, Canvas Scaler, 마스크와 동적 텍스트 크기를 함께 점검한다.
좌우 외곽 여백과 카드 사이 간격을 상단 HUD의 기준값으로 통일하고, 스프라이트 종횡비와 외곽선 두께를 유지한 상태에서 수정하라.

P-28. 머지 충돌 안전 해결

활용 목적: 협업 변경과 기존 UI 보존

현재 Git 머지 충돌을 확인하고 Unity YAML, 폰트 에셋과 meta GUID가 손상되지 않도록 해결하라.
한쪽 파일을 통째로 선택하기 전에 양쪽 변경의 목적을 비교하고, 기존에 완성된 UI와 팀원의 기능을 모두 보존할 수 있도록 수동 병합한다.
충돌 마커 제거, 참조 GUID, 씬 계층, 컴파일과 주요 UI 표시를 검증하고 사용자의 관련 없는 미커밋 변경은 수정하지 않는다.

P-29. 이미지 품질 반복 보정

활용 목적: 생성 이미지의 실사용 품질 확보

생성된 캐릭터 스프라이트를 원본과 비교하여 포즈, 하체 비율, 손·발, 중심 좌표, 크기와 투명 경계를 검수하라.
초록색 잔상, 잘린 머리카락·소품, 프레임 간 위치 흔들림과 해상도 저하가 있으면 원인을 구분해 보정한다.
이미 승인된 얼굴과 디자인은 유지하며, 수정 결과를 적용하기 전에 별도 프리뷰로 제시해야 하는 요청에서는 실제 게임 에셋을 변경하지 않는다.

P-30. 요청 철회 및 안전한 롤백

활용 목적: 실험적 변경의 선택적 복원

직전 요청으로 적용한 변경만 식별하여 이전 상태로 되돌려라.
예를 들어 캐릭터 애니메이션을 제거하라는 경우 애니메이션 시트, 재생 코드와 연결만 제거하고, 그 이전에 완성된 단일 스프라이트와 다른 UI 변경은 유지한다.
Git 전체 초기화나 관련 없는 파일의 덮어쓰기를 사용하지 말고, 롤백 후 컴파일과 런타임 참조를 확인하라.

12. 반복 피드백에 사용한 공통 프롬프트 형식

실제 개발 과정에서는 아래 구조로 화면 문제를 관찰하고 개선 요청을 반복하였다.

[현재 문제]
현재 화면에서 발생하는 잘림, 겹침, 비율 불일치 또는 동작 오류를 구체적으로 설명한다.

[목표 상태]
참고 이미지 또는 인접 UI를 기준으로 원하는 위치, 크기, 간격과 동작을 명시한다.

[보존 조건]
기존 스프라이트 종횡비, 데이터 연동, 이미 완성된 UI와 팀원의 변경 사항은 유지한다.

[검증 조건]
Unity Play Mode에서 대상 기능과 연관 기능을 함께 확인하고, 컴파일 오류와 새로운 레이아웃 회귀가 없는지 점검한다.

13. 프롬프트 작성 원칙

  1. 컨텍스트 선행: 관련 기획서와 기존 코드를 먼저 확인하도록 지시하였다.
  2. 목표의 구체화: 위치, 크기, 시간, 해상도, 상태값과 같은 측정 가능한 기준을 제시하였다.
  3. 보존 범위 명시: 기존 UI, 팀원의 구현, 데이터 연결과 이미지 종횡비를 유지하도록 제한하였다.
  4. 동적 확장 고려: 아이템, 슬롯, 상품, 스킬과 코스튬 추가·삭제에 자동 대응하도록 요구하였다.
  5. 단계적 시각 검수: 이미지 작업은 프리뷰 승인 후 적용하고, 필요 시 반복 보정하였다.
  6. 실행 검증 포함: 코드 작성뿐 아니라 Unity 컴파일, Play Mode 동작과 화면 회귀를 확인하도록 하였다.
  7. 안전한 협업: 머지 충돌과 롤백 시 관련 없는 사용자 변경을 보존하도록 요구하였다.

14. 정리

본 프로젝트에서는 생성형 AI를 단순 코드 자동 완성 도구가 아니라 기획 문서 분석, 시스템 구현, UI 조립, 이미지 에셋 제작, 디버깅과 반복 품질 개선을 수행하는 협업 도구로 활용하였다. 각 프롬프트는 기존 프로젝트의 맥락과 보존 조건을 제공하고, 구현 이후 실제 게임 화면에서 발견한 문제를 구체적인 후속 피드백으로 수정하는 방식으로 운용하였다.
