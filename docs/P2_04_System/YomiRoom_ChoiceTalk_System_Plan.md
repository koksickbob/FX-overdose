## 1. 요약

요미의 방 `DialoguePanel`의 **입력형 자유 채팅을 폐지하고 선택형 일상 대화로 개편**한다. 일상 대화가 끝나면 그 흐름 위에서 **당일 차트 방향성 힌트**로 이어진다.

**현황 검증 결과: 작동 여부를 확인할 대상이 아직 없다.** 선택지형 시스템은 코드가 0줄이고, 지금 패널이 하는 일은 무엇을 입력하든 고정된 한 줄을 돌려주는 것뿐이다.

그리고 **저장 커버리지에 구멍이 있다.** 대화 진행 상태(시나리오 번호, 노드 위치, 선택 이력)가 세이브에 하나도 없는데, **대화 도중 자동 저장은 이미 일어나고 있다.** 이 조합은 호감도 파밍 구멍을 만든다 (4.3절).

## 3. 시스템 설계

### 3.1. 시나리오 번호 체계

대화 단위를 **시나리오(Scenario)** 로 부르고 고유 번호를 붙인다. 저장·디버그·작가 커뮤니케이션의 공통 키가 된다.

```
TALK_<카테고리>_<3자리>        예: TALK_MEAL_001, TALK_JEALOUSY_004
HINT_<Regime>_<티어>_<2자리>   예: HINT_BULL_T2_03
```

| 카테고리 | 접두사 | 기존 `DailyDialogueCategory` 대응 |
| --- | --- | --- |
| 인사/일상 | `TALK_GREET_` | `Greeting` |
| 식사 | `TALK_MEAL_` | `Eating` |
| 수면/휴식 | `TALK_SLEEP_` | `Sleeping` |
| 놀이 | `TALK_PLAY_` | `Playing` |
| 삐짐/분노 | `TALK_ANGER_` | `Anger` |
| 애정/집착 | `TALK_LOVE_` | `Affection` |
| 힌트 | `HINT_` | — |

**번호는 영구 식별자다.** 대사를 고쳐도 번호는 유지하고, 시나리오를 폐기해도 번호를 재사용하지 않는다. 세이브에 기록되기 때문이다.

### 3.2. 구조

```csharp
// Assets/Scripts/DatingSim/Dialogue/YomiTalkTopics.cs (신규)
public readonly struct TalkChoice   // 플레이어 선택지
{
    public readonly string Text;        // 25자 이내
    public readonly int Affection;      // +0 ~ +3
}

public readonly struct TalkNode      // 요미 대사 1개 + 선택지 2~4개
{
    public readonly string YomiLine;    // 60자 이내
    public readonly TalkChoice[] Choices;
}

public readonly struct TalkTopic     // 시나리오 1편 = 노드 2~4개
{
    public readonly string Id;          // TALK_MEAL_001
    public readonly TalkCategory Category;
    public readonly TalkNode[] Nodes;
    public readonly string ClosingLine; // 마무리 대사
}
```

### 3.3. 대화 개시 — 누가 먼저 말을 거는가

**둘 다 있다.** 상황에 따라 갈린다.

| 개시 주체 | 트리거 | 동작 |
| --- | --- | --- |
| **요미가 먼저** | 방 진입 시 / 슬롯을 크게 소모하고 돌아왔을 때 / 하루의 첫 진입 | 선제 대사 1줄을 말풍선에 띄운다. **선택지는 뜨지 않는다** — 대화를 열지 않고 분위기만 만든다 |
| **플레이어가 먼저** | `자유대화` 버튼 | 슬롯 1 소모 → 토픽 추첨 → 노드 1 진입 → 선택지 표시 |

선제 대사는 **자원을 소모하지 않고 호감도도 주지 않는다.** 방에 들어올 때마다 파밍되면 안 되기 때문이다.

### 3.4. 진행 흐름 — 일상 대화에서 차트 힌트로

```
[자유대화 버튼]  슬롯 -1
      │
      ▼
[토픽 추첨]  당일 미사용 + 조건 통과 풀에서 1개
      │
      ▼
[노드 1] 요미 대사 ─► 선택지 2~4개 ─► 선택 ─► 호감도 +0~3
      │                                          gainToday 누적
      ▼
[노드 2] …  (토픽마다 2~4노드)
      │
      ▼
[토픽 종료] ClosingLine
      │
      ├─ gainToday < 4 ──────────► 대화 종료
      │
      └─ gainToday ≥ 4 ──► [힌트 시나리오로 자연 연결]
                                │
                                ▼
                     DailyMarketOutlook.GetOrRoll(오늘)
                                │
                                ▼
                     티어 판정 → HINT_* 대사 1줄 출력
                                │
                                ▼
                     MarkRevealed() → 당일 차트가 그 방향으로 잠김
```

**"자연스럽게 이어진다"의 구현**: 힌트는 별도 UI를 띄우지 않는다. 같은 말풍선 로그에 요미의 대사가 **한 줄 더 이어지는 형태**다. 플레이어 입장에서는 일상 대화 끝에 요미가 무심코 흘리는 예감으로 읽힌다.

### 3.5. 상태 머신

`YomiRoomState`를 재사용한다. `Chatting`(선택 대기) / `Responding`(선택 처리·연출) 의미만 바뀐다.

| 상태 | 의미 |
| --- | --- |
| `Idle` | 방 탐색 중 |
| `Chatting` | **선택지 표시 중, 플레이어 입력 대기** |
| `Responding` | 선택 처리 → 다음 노드 대사 출력 중 |
| `Transitioning` | 씬 이동 |

## 4. 저장 테이블 검증 ⚠️

### 4.1. 현재 `SaveData`에 있는 대화 관련 필드 — 3개뿐

| 필드 | 의미 |
| --- | --- |
| `TalkAffectionGainToday` | 당일 대화로 획득한 호감도 합계 |
| `TalkHintIssuedDay` | 힌트를 발급한 일차 |
| `TalkTopicsUsedToday` | 당일 소비한 토픽 ID 목록 |

### 4.2. 누락 — 요청하신 항목은 **전부 빠져 있다**

| # | 누락 상태 | 없으면 벌어지는 일 |
| --- | --- | --- |
| **T1** | **진행 중인 시나리오 번호** | 대화 도중 종료하면 어느 토픽이었는지 모른다 |
| **T2** | **현재 노드 인덱스 (대사별 진행도)** | 어디까지 진행했는지 모른다. 재개 불가 |
| **T3** | **플레이어 선택지 이력** | 무엇을 골랐는지 기록이 없다. 선택에 따른 후속 분기·회상·성향 판정이 불가능 |
| **T4** | **발급된 힌트의 티어와 대사 번호** | `TalkHintIssuedDay`는 "줬다"만 안다. 로드 후 같은 힌트를 다시 보여줄지 다른 걸 줄지 결정할 근거가 없다 |
| **T5** | **누적 소비 토픽 이력** | `TalkTopicsUsedToday`는 **당일만**이다. 20일 내내 같은 토픽이 반복돼도 막을 수 없다 |
| **T6** | **시나리오 완료 플래그** | 휴면 `ScenarioEntry`에 `setFlagsOnComplete` 개념이 있으나 대응 필드가 없다. "고백 이벤트를 봤는가" 같은 분기 조건을 세울 수 없다 |
| **T7** | **선제 발화 이력** | 방에 들어올 때마다 같은 인사를 반복한다 |

### 4.3. ⚠️ 가장 위험한 조합 — 중단된 대화의 호감도 파밍

**대화 도중 자동 저장이 이미 일어난다.** `DatingTimeManager.ModifyAffection()`이 호출될 때마다 `SaveCurrentGame()`을 부르기 때문이다([DatingTimeManager.cs:138-143](../../Assets/Scripts/DatingSim/Core/DatingTimeManager.cs#L138-L143)). 즉 **노드를 하나 넘길 때마다 저장된다.**

그런데 `TalkTopicsUsedToday`에 토픽 ID가 들어가는 시점을 **대화 종료 시**로 잡으면 이렇게 된다.

```
노드 1 선택 → 호감도 +3 → 자동 저장  (토픽은 아직 '사용됨'이 아님)
   │
   └─ 여기서 게임 종료 / 씬 이탈
        │
        ▼
   재접속 → 호감도 +3은 남아 있고, 토픽은 여전히 미사용
        │
        ▼
   같은 토픽을 다시 열어 +3 재획득 → 무한 반복
```

**해결 원칙: 토픽을 여는 순간 소비 처리한다.** 슬롯 차감과 `TalkTopicsUsedToday` 추가를 **노드 1 진입 전에** 끝내고, 중단된 대화는 재개하지 않고 버린다. 중도 이탈로 얻은 호감도는 그대로 두되 **같은 토픽을 다시 열 수 없게** 하는 것이 가장 단순하고 구멍이 없다.

### 4.4. 추가할 `SaveData` 필드

```csharp
// --- 요미 선택형 대화 진행 상태 ---
public string TalkActiveTopicId = "";          // 진행 중인 시나리오 번호. 없으면 빈 문자열 (T1)
public int TalkActiveNodeIndex = -1;           // 현재 노드 위치 (T2)
public List<string> TalkChoiceHistory = new List<string>();  // "TALK_MEAL_001:0:2" = 토픽:노드:선택 (T3)

// --- 힌트 발급 내역 ---
public int TalkHintTier = 0;                   // 0=미발급 / 1=모호 / 2=명시 (T4)
public string TalkHintLineId = "";             // 실제로 출력한 힌트 대사 번호 (T4)

// --- 누적 이력 ---
public List<string> TalkTopicsSeenTotal = new List<string>();   // 전체 플레이 소비 이력 (T5)
public List<string> TalkCompletedFlags = new List<string>();    // 시나리오 완료 플래그 (T6)
public int TalkLastGreetingDay = -1;           // 선제 인사를 마지막으로 한 일차 (T7)
```

**`TalkChoiceHistory` 형식**: `"<토픽ID>:<노드>:<선택인덱스>"` 문자열 1줄 = 선택 1회. `JsonUtility`가 중첩 구조를 직렬화하지 못하므로 문자열 인코딩을 쓴다. 프로젝트가 이미 쓰는 병렬 리스트 관례([SaveData.cs](../../Assets/Scripts/System/SaveData.cs)의 `ActiveItemIds`/`ActiveItemLevels`)와 같은 이유다.

> **용량 주의**: 20일 × 하루 2회 × 노드 3개 = 약 120줄. 문제 없는 규모다. 다만 **무한히 쌓이지 않도록** 상한(예: 300줄)을 두고 오래된 것부터 버린다.

### 4.5. 일차 전환 시 리셋 대상

`GameManager.FinalizeProceedToNextDay()` → `DatingTimeManager.SyncToNewDay()` 경로에서 함께 비운다.

| 리셋 | 유지 |
| --- | --- |
| `TalkAffectionGainToday` → 0 | `TalkTopicsSeenTotal` |
| `TalkTopicsUsedToday` → 비움 | `TalkChoiceHistory` |
| `TalkActiveTopicId` / `TalkActiveNodeIndex` → 초기화 | `TalkCompletedFlags` |
| `TalkHintTier` / `TalkHintLineId` → 초기화 | `DatingAffection`(누적 호감도) |

`OutlookDay`가 바뀌면서 힌트가 자동 무효화되는 것과 짝을 이룬다 (상위 계획 `S13`).

| 힌트 반영 | `Q2` 승인분 적용 — `Revealed`인 날은 `SwitchToRandomRegime()`의 **역방향 분기를 Sideways로 흡수** |
| 파밍 차단 | `TryStartTalk()`이 **첫 노드 진입 전에** 슬롯 차감 + `TalkTopicsUsedToday`/`TalkTopicsSeenTotal` 기록 (4.3절 `TS1`) |
| 선제 발화 | `TryGreetOnEnter()` — 하루 1회, **자원·호감도 소모 없음** |
| 힌트 연결 | `OnTalkFinished(마무리, 힌트)` 한 이벤트로 전달. UI가 **같은 말풍선 로그에 한 줄 더** 얹는다. 별도 팝업 없음 |
| 폐지 | `IYomiDialogueProvider` / `PlaceholderDialogueProvider` **파일째 삭제**. 입력창·전송 버튼은 `SetActive(false)` |
| 검사 | `yomi_dialogue_lint.py`에 **구조 계약 검사 추가** — 노드 2~4 / 선택지 2~4 / 노드당 +3 정확히 1개 / 선택지 25자 / 힌트 풀 8칸 5줄 이상 / Squeeze 방향 단어 금지 |

> 구조 검사기가 **작성 직후 실제 결함을 잡았다** — `TALK_LOVE_001` 마지막 노드에 +3 선택지가 둘이었다. 수정 후 위반 0.

**미구현**: 대화 도중 이탈 시 재개. 설계상 재개하지 않는다(`TS1`). `TalkActiveTopicId`/`TalkActiveNodeIndex`는 **어디서 끊겼는지 기록용**으로만 남긴다.

### 5.2. 씬 단독 재생 지원 (2026-08-13 추가)

`SaveLoadManager`는 `TitleScene`에만 배치돼 있어(`SV-C6`), **에디터에서 요미의 방 씬만 열어 재생하면 `Instance`가 null**이다. 이 경우 진행 상태를 담을 곳이 없어 **대화는 되는데 힌트가 영영 나오지 않았다.** 당일 획득 호감도(`TalkAffectionGainToday`)가 세이브에 쌓이는 값이기 때문이다.

`YomiRoomManager.ProgressData` 프로퍼티를 두어 해결했다.

| 상황 | 사용하는 데이터 |
| --- | --- |
| 정상 플로우 (타이틀 → GameScene → 정산 → 요미의 방) | `SaveLoadManager.CurrentData` (실제 세이브) |
| **씬 단독 재생** | 세션 한정 임시 `SaveData` + 경고 로그 1회 |

임시본은 **디스크에 기록되지 않으므로 실제 세이브를 건드릴 위험이 없다.** `SaveLoadManager`가 없으면 저장 경로 자체가 동작하지 않기 때문이다. `DailyMarketOutlook`도 `Persist()`가 세이브 부재 시 조용히 넘어가므로 방향성은 메모리에서만 굴러간다.

> 이 덕분에 **요미의 방 씬만 열어도 인사 → 대화 → 선택 → 호감도 → 힌트까지 전 구간을 확인**할 수 있다.

## 8. 호감도 기반 토픽 해금 — 구현 계획

> **결정**: `Q-T5` 대사 전면 분기 대신 **토픽 단위 해금**으로 확정 (2026-08-13)
> **원칙**: 호감도는 **무슨 얘기를 하는지**를 정하고, 집착도는 **얼마나 세게 말하는지**를 정한다 (바이블 5.3절과 축이 겹치지 않음)

### 8.1. 왜 대사 분기가 아니라 토픽 해금인가

| | 대사 전면 분기 | **토픽 해금** |
| --- | --- | --- |
| 대사 물량 | 18줄 → 200줄 이상 | **추가 0줄** |
| 체감 | 같은 얘기를 말투만 바꿔서 반복 | **꺼내는 화제 자체가 달라짐** |
| 어색함 | 호감도 10에 "오빠는 내 거야"가 나올 수 있음 | 구조적으로 불가능 |
| 유지보수 | 노드마다 변형 × 구간 수 | 토픽에 필드 2개 |

일상 대사는 친밀도에 따라 실제로 크게 달라지지 않는다. "밥 먹었어?"는 호감도 10이든 90이든 같은 문장이다. **관계 진전의 체감은 말투가 아니라 화제에서 온다.**

### 8.2. 구간 설계

| 구간 | 호감도 | 열리는 토픽 | 성격 |
| --- | --- | --- | --- |
| **1단계** | 0 ~ 30 | `TALK_GREET_001` · `TALK_MEAL_001` · `TALK_PLAY_001` | 가벼운 일상. 아직 거리감이 있다 |
| **2단계** | 31 ~ 60 | + `TALK_SLEEP_001` · `TALK_ANGER_001` | 투정과 삐짐. 감정을 드러내기 시작 |
| **3단계** | 61 ~ 100 | + `TALK_LOVE_001` | 집착과 애정. 요미의 본색 |

**상한(`MaxAffection`)은 이번에 쓰지 않는다.** 초반 전용 토픽을 후반에 닫으면 "본 적 없는 토픽을 영영 못 보는" 경우가 생긴다. 필드는 만들되 전부 100으로 두고, 필요해지면 그때 조인다.

### 8.3. 초반 대화 물량 점검

노드 수 × 최대 +3 기준 획득량이다. 힌트 임계는 티어1 = 4, 티어2 = 7.

| 토픽 | 노드 | 최대 획득 | 해금 단계 |
| --- | --- | --- | --- |
| `TALK_GREET_001` | 2 | +6 | 1 |
| `TALK_MEAL_001` | 3 | +9 | 1 |
| `TALK_PLAY_001` | 4 | +12 | 1 |
| `TALK_SLEEP_001` | 3 | +9 | 2 |
| `TALK_ANGER_001` | 4 | +12 | 2 |
| `TALK_LOVE_001` | 3 | +9 | 3 |

**1단계에서도 티어2 힌트에 도달할 수 있다** (`MEAL`/`PLAY` 한 판이면 +7 이상). 초반부터 힌트가 막히지 않으므로 진행이 정체되지 않는다.

다만 **1단계 후보가 3개뿐**이라 하루 2회 대화하면 이틀이면 한 바퀴 돈다. 반복 체감을 줄이려면 이미 있는 `TalkTopicsSeenTotal`을 이용해 **최근에 본 토픽을 후순위로** 미는 정도면 충분하다. 토픽을 더 쓰는 건 그 다음이다.

### 8.4. ⚠️ 저장 테이블 영향 분석

**핵심 질문: 해금 판정을 무엇으로 하는가.** 여기서 신규 필드 필요 여부가 갈린다.

#### 문제 — 현재 호감도로 판정하면 토픽이 다시 잠긴다

`ModifyAffection()`은 음수를 받을 수 있고 0~100으로 클램프된다. 선택지는 마이너스를 주지 않지만(`S9`), 앞으로 집착 이벤트·데이트 실패 등이 호감도를 깎을 수 있다.

```
호감도 62 → TALK_LOVE_001 해금 → 대화 진행
   ↓ (다른 시스템이 호감도 -5)
호감도 57 → TALK_LOVE_001 다시 잠김 → 진행하던 화제가 사라짐
```

**해결: 역대 최고 호감도(peak)로 판정한다.** 한 번 열린 토픽은 닫히지 않는다. 트레이딩 파트의 `PeakBalance`와 같은 발상이다.

#### 추가할 `SaveData` 필드 — 2개

```csharp
// --- 호감도 기반 토픽 해금 ---
public int TalkPeakAffection = 0;      // 역대 최고 호감도. 해금 판정의 기준 (필수)
public int TalkAffectionTierSeen = 0;  // 플레이어가 인지한 해금 단계. 승급 연출용 (선택)
```

`TalkAffectionTierSeen`은 "요미가 새 화제를 꺼내며 관계 진전을 언급하는" 연출을 붙일 때 쓴다. 지금 당장 필요하지는 않지만 **스키마를 두 번 깨지 않으려고 같이 넣는다.**

#### 저장 커버리지 전수 확인

| 필요한 상태 | 저장 위치 | 상태 |
| --- | --- | --- |
| 현재 호감도 | `DatingAffection` | ✅ 기존 |
| **역대 최고 호감도** | `TalkPeakAffection` | 🆕 **신규 필수** |
| **인지한 해금 단계** | `TalkAffectionTierSeen` | 🆕 신규(연출용) |
| 당일 소비 토픽 | `TalkTopicsUsedToday` | ✅ 기존 |
| 누적 소비 이력 (반복 회피) | `TalkTopicsSeenTotal` | ✅ 기존 |
| 완료 시나리오 | `TalkCompletedFlags` | ✅ 기존 |
| 당일 획득 호감도 | `TalkAffectionGainToday` | ✅ 기존 |
| 힌트 발급 내역 | `TalkHintIssuedDay` / `TalkHintTier` / `TalkHintLineId` | ✅ 기존 |
| 진행 중 시나리오 | `TalkActiveTopicId` / `TalkActiveNodeIndex` | ✅ 기존 |
| 선택 이력 | `TalkChoiceHistory` | ✅ 기존 |
| 선제 발화 이력 | `TalkLastGreetingDay` | ✅ 기존 |
| 해금 구간 경계값(0/31/61) | — | **저장 안 함.** 코드 상수. 저장하면 이중 진실 원천이 된다 |
| 토픽별 `MinAffection` | — | **저장 안 함.** `YomiTalkTopics` 정적 테이블에 있는 정의값 |

#### 마이그레이션 — 이번엔 백필이 실제로 필요하다

지금까지의 신규 필드는 초기화자 기본값으로 충분했지만, **`TalkPeakAffection`은 0으로 두면 안 된다.** 기존 세이브에서 호감도 70인 플레이어가 로드하자마자 1단계로 강등된다.

```csharp
// SaveDataMigrator, 1.6.0 게이트 안
if (data.TalkPeakAffection < data.DatingAffection)
    data.TalkPeakAffection = data.DatingAffection;
```

이 한 줄이 **신규 세이브·구버전 세이브 양쪽을 동시에 처리한다.** 신규는 둘 다 0이라 무해하고, 구버전은 현재 호감도로 채워진다.

#### 리셋 규칙

| 일차 전환 시 | 새 게임 시 |
| --- | --- |
| `TalkPeakAffection` **유지** (누적값) | 0으로 초기화 |
| `TalkAffectionTierSeen` **유지** | 0으로 초기화 |

일차가 바뀐다고 해금이 풀리면 안 된다. 5.1절의 `TalkAffectionGainToday` / `TalkTopicsUsedToday` 리셋 대상과 **명확히 구분**한다.

| **U-3** | `DatingTimeManager`가 `peakAffection`을 필드로 보유. `ModifyAffection()`에서 갱신하고 `LoadFromSaveData`/`SaveToData`로 왕복. **호감도의 주인이 갱신하므로 대화 외 경로(이벤트·데이트)로 올라도 누락되지 않는다** |
| **U-4** | `TalkTopic`에 `MinAffection`/`MaxAffection` + `IsUnlocked(peak)` 추가. 6개 토픽에 구간값 지정 (0 / 31 / 61, 상한은 전부 100) |
| **U-5** | `PickTopic()`에 해금 필터 + **미열람 토픽 우선** 로직. `TryStartTalk()`의 슬롯 차감을 추첨 뒤로 이동 (`TS11`) |
| **U-6** | 린터에 **"호감도 0에서 열리는 토픽 최소 2개"** 검사 추가 (`TS10`). 현재 3개로 통과 |

**이중 안전망**: `LoadFromSaveData`에서도 `peakAffection = max(TalkPeakAffection, DatingAffection)`로 받는다. 마이그레이터를 타지 않는 경로(수동 편집 세이브 등)에서도 현재 호감도보다 낮은 peak가 들어오지 않는다.

**리셋 확인**: `SyncToNewDay()`는 peak를 건드리지 않는다(일차 전환에 유지). 새 게임에서는 `LoadFromSaveData`가 호출되지 않아 필드 기본값 0으로 시작한다.

**검증**: `python yomi_dialogue_lint.py` 통과 (구조 위반 0, 시작 해금 토픽 3개), `Assembly-CSharp` 클린 컴파일. 세이브 왕복 검사기는 `SaveData`의 public 필드를 리플렉션으로 전수 순회하므로 신규 2개 필드도 자동으로 검사 범위에 들어간다.

## 9. 대화 밀도 개편 — "요미가 기계적으로 말한다"

> **발의**: 2026-08-13. 플레이어 선택지 전면 교체(바이블 2.2절) 직후, **요미 쪽 대사가 부자연스럽다**는 지적
> **제기된 진단**: 화제가 단순하고 `요미 → 플레이어 → 요미 → 플레이어` 1:1 교대가 반복돼 요미가 빈약해 보인다
> **상태**: 기획 확정 대기

### 9.1. 진단 — 데이터를 세어봤다

제기된 진단은 맞다. 그리고 **원인이 하나가 아니라 셋**이다.

| 측정 항목 | 실측값 |
| --- | --- |
| 요미의 대사 총량 | **25줄** (노드 19 + 마무리 6). 인사 1줄·힌트 40줄 별도 |
| 플레이어 선택지 총량 | **57개** |
| 한 토픽 1회 플레이에서 요미가 띄우는 말풍선 | **3~5개** |
| **선택에 따라 요미의 다음 대사가 달라지는 경우** | **0건** |
| 전 노드의 선택지 개수 | **전부 3개** (19/19) |
| `+3` 선택지가 마지막 칸인 노드 | **15/19** |
| 차트 인격(바이블 3.5절) 토픽 | **0개** |

**말하는 쪽이 듣는 쪽보다 대사가 적다.** 히로인의 대사가 25줄인데 플레이어 선택지가 57개다.

| ID | 원인 | 왜 기계적으로 들리는가 |
| --- | --- | --- |
| **C-1** | **1노드 = 1말풍선** | 구조가 강제한다. 바이블 3.2절의 핵심인 **"위축 → 우쭐이 한 대사 안에서 뒤집힌다"** 는 말풍선 하나로는 리듬이 안 산다. 요미의 가장 요미다운 특징이 자료구조 때문에 표현되지 못하고 있다 |
| **C-2** | **선택의 결과가 대사에 없다** ⚠️ **가장 큼** | `너부터 챙겨`를 고르든 `너랑 같이 먹으려고 참았어`를 고르든 **요미의 다음 대사가 글자 하나까지 같다.** 대화가 아니라 **점수가 숨겨진 메뉴판**으로 읽힌다 |
| **C-3** | **리듬이 고정** | 노드마다 예외 없이 선택지 3개, `+3`은 대개 맨 아래. 두세 번이면 "제일 긴 마지막 걸 누르면 된다"가 학습된다. **린터가 `+3 정확히 1개`를 강제하고 있어** 구조적으로 굳었다 |
| **C-4** | **화제 축이 하나뿐** | 토픽 6개가 전부 **"요미가 오빠에게 무언가를 요구"** 하는 구조다 (밥 먹었어 / 놀아줘 / 같이 자자 / 화났어 / 없으면 못 살아 / 생각했어?). 요미가 **자기 얘기를 하는 토픽이 0개**, **차트 얘기를 먼저 꺼내는 토픽이 0개** |
| **C-5** | **물량** | 토픽 6개. 하루 2회 대화하면 **3일이면 한 바퀴** 돈다. 게임은 20일이다 |

> **C-4의 부작용 하나**: 힌트가 밥 얘기 끝에 튀어나온다. `요미가 만든 거면 뭐든 맛있어` → `오늘은 위야! 요미 감각 믿어!` 는 **화제 전환이 아니라 문맥 단절**이다. 차트 토픽이 없어서 생긴 문제다.

### 9.2. 설계 — 레버 3개 + 확장 2개

비용 대비 체감 순으로 정렬했다.

| ID | 레버 | 코드 비용 | 대사 비용 | 체감 |
| --- | --- | --- | --- | --- |
| **R-1** | **버스트** — 노드 1개가 말풍선 1~3개 | 구조체 필드 1 + UI 코루틴 | **0줄** (기존 줄을 쪼개기만 해도 성립) | 큼 |
| **R-2** | **즉답** — 고른 선택지에 요미가 바로 반응 | 필드 1 + 이벤트 1 | 57줄 | **가장 큼** |
| **R-3** | **리듬 변주** — 선택지 2~4개 섞기, `+3` 위치 섞기 | 0 | 0줄 | 중간 |
| **R-4** | **화제 축 확장** — 차트/자기얘기/사물 토픽 | 열거형 1줄 | 토픽당 ~15줄 | 큼 |
| **R-5** | **밀도** — 토픽을 화제가 아니라 **장면**으로 | 린터 상한 조정 | **10장 참조** | 큼 |

#### R-1. 버스트 — 새 대사를 안 써도 리듬이 생긴다

지금 대사는 **이미 세 박자짜리를 한 줄에 눌러 담고 있다.**

```
현재 :  요미 ▌오빠! 밥은 먹고 다니는 거야? 요미가 굶지 말라고 했지!
        └─ 말풍선 1개

버스트:  요미 ▌오빠!
        요미 ▌밥은 먹고 다니는 거야?
        요미 ▌요미가 굶지 말라고 했지!
        └─ 말풍선 3개. 새로 쓴 글자 0자
```

메신저에서 사람은 문장을 완성해서 보내지 않는다. **끊어서 연달아 보낸다.** 요미처럼 감정이 앞서는 캐릭터라면 더 그렇다. 이건 연출이 아니라 캐릭터 표현이다.

**버스트 줄 규칙**

| 항목 | 값 |
| --- | --- |
| 노드당 줄 수 | **1~3줄** (4줄부터는 읽는 사람이 기다림으로 느낀다) |
| 한 줄 길이 | **30자 이하 권장**, 60자 상한(바이블 4.3절 일상 대사) |
| 출력 간격 | **0.4초** — "타이핑 중"으로 읽히는 구간. 1초를 넘기면 "대기"가 된다 |
| 출력 중 | 선택지 숨김. 기존 `YomiRoomState.Responding` 재사용 |

#### R-2. 즉답 — 선택지에 결과를 붙인다

`TalkChoice`에 요미의 반응 1줄을 단다. **고른 선택지의 것만 출력**된다.

```
요미 ▌오빠!
요미 ▌밥은 먹고 다니는 거야?
요미 ▌요미가 굶지 말라고 했지!
   ├ [너부터 챙겨. 난 괜찮아.]        +0  →  요미 ▌또 그 소리! 요미는 오빠 챙기는 게 일이라구!
   ├ [아직... 그럴 정신이 없었어.]     +1  →  요미 ▌그럴 줄 알았어... 오빠는 요미 없으면 큰일이야.
   └ [너랑 같이 먹으려고 참았어.]      +3  →  요미 ▌...뭐야. 그런 말 하면 요미가 못 참잖아!
                                              │
                                              ▼
                                        [노드 2] 그럼 지금 만들어 줄게! …
```

**물량 효과가 크다.**

| | 현재 | 즉답 도입 후 |
| --- | --- | --- |
| 요미 대사 총량 | 25줄 | **82줄** (+57) |
| 신규 토픽 | — | **0개** |
| 한 토픽의 경로 가짓수 | 1 | **3³ = 27** (3노드 기준) |

**같은 토픽을 다시 열어도 다른 대화가 된다.** C-5(물량)를 토픽을 안 쓰고 완화하는 유일한 수단이다.

> **즉답과 다음 노드의 역할 분담** — 즉답은 **방금 고른 말에 대한 반응만** 한다. 화제를 옮기지 않는다. 화제 전환은 다음 노드의 첫 줄이 맡는다. 이걸 안 지키면 즉답과 다음 노드가 같은 말을 두 번 하게 된다 (`TS15`).

#### R-3. 리듬 변주 — 비용 0

| 규칙 | 현재 | 개편 |
| --- | --- | --- |
| 노드당 선택지 수 | 전부 3 | **2~4 혼합.** 감정이 몰린 노드는 2개(양자택일), 여유로운 노드는 4개 |
| `+3` 위치 | 15/19가 마지막 칸 | **토픽 안에서 위치를 흩는다.** 린터가 "한 토픽의 `+3`이 전부 같은 인덱스면 경고" |
| `+3` 개수 | 노드당 정확히 1개 | **유지.** 호감도 총량이 힌트 임계(4/7)와 직결돼 예측 가능해야 한다 (`Q-T9`) |

#### R-4. 화제 축 확장 — 요미의 절반이 빠져 있다

`TalkCategory`에 항목을 더한다. 번호 체계는 3.1절 규칙 그대로.

| 신규 접두사 | 축 | 왜 필요한가 |
| --- | --- | --- |
| **`TALK_CHART_`** | **차트 인격** (바이블 3.5절) | **최우선.** 요미의 인격 전환은 이 캐릭터의 전부인데 데이팅 파트에 0개다. 게다가 **힌트가 자연스럽게 연결된다** — 차트 얘기 끝에 나오는 예감은 문맥 단절이 아니다 |
| **`TALK_SELF_`** | 요미가 **자기 얘기**를 한다 | 요구가 아니라 공유. 오늘 뭘 했는지, 뭘 망쳤는지(덤벙 축, 바이블 3.3절). 6토픽 전부가 요구형인 C-4를 직접 깬다 |
| **`TALK_JEALOUS_`** | 질투 (바이블 3.4절) | `Anger`와 다르다. 삐짐은 오빠를 향하고, 질투는 **오빠의 관심을 가져간 대상**을 향한다 |
| `TALK_ROOM_` | 방의 사물 | 탑다운 방 상호작용과 붙일 때. **1차에서는 보류** |

> `TALK_CHART_`는 카테고리 성격상 **차트 인격 = 단정적·명령형·도박꾼 어휘**로 쓴다. 일상 토픽과 톤이 확연히 달라야 값어치가 있다. 여기서만 요미가 주도권을 쥔다.

#### R-5. 밀도 — 토픽 개수보다 토픽의 길이가 먼저다

**⚠️ 이 항목은 10장으로 대체됐다 (2026-08-13 개정).**

초안은 "토픽 6 → 12~15개"였다. 개수만 늘리면 **짧고 기계적인 대화가 15편**이 될 뿐이다. 문제는 개수가 아니라 **한 편의 밀도**다 — 지금 한 판은 요미 말풍선 3~5개로 끝난다. 소설의 한 장면이 아니라 알림창에 가깝다.

노드 상한(현재 2~4), 호감도 배분, 물량 목표, 작성 지침은 **[10장](#10-대사-밀도-라이트-노벨-수준으로--작성-지침)** 에서 다시 잡는다.

### 9.3. 데이터 구조 변경

```csharp
public readonly struct TalkChoice
{
    public readonly string Text;        // 25자 이내 (버튼 1줄)
    public readonly int Affection;      // +0 ~ +3
    public readonly string Reply;       // 🆕 요미의 즉답 1줄. null이면 생략 (R-2)

    // 기존 57개 호출부가 그대로 컴파일되도록 선택 인자로 둔다.

public readonly struct TalkNode
{
    public readonly string[] YomiLines; // 🔧 string → string[]. 1~3줄 (R-1)
    public readonly TalkChoice[] Choices;
```

## 10. 대사 밀도 — 라이트 노벨 수준으로 + 작성 지침

> **발의**: 2026-08-13. 9장 검토 후 **"개수가 너무 적다. 라이트 노벨이나 연애 소설의 대화 부분을 읽는 것처럼 상황과 대화가 풍부하고 자연스러워야 한다"**
> **효력**: 9.2절 `R-5`(물량 목표)를 **대체**한다. `Q-T9`(호감도 배분)를 **뒤집는다**
> **상태**: 기획 확정 대기

### 10.1. 기준을 다시 잡는다 — 지금은 장면이 아니라 알림창이다

| | 현재 한 판 | 라이트 노벨 한 장면 |
| --- | --- | --- |
| 요미 말풍선 | **3~5개** | 20~40 |
| 플레이어 발화 | 2~4회 | 5~10 |
| 상황 서술 | **0** | 대사 사이사이 |
| 화제 | 하나, 직선 | 새고 돌아온다 |
| 읽는 시간 | **20초** | 2~3분 |

**소비 자원은 시간 슬롯 1칸으로 같다.** 밥 한 끼, 알바 한 탕과 같은 값을 치르고 20초를 받는다. 교환비가 안 맞는다.

**참고 기준이 이미 프로젝트 안에 있다.** 트레이딩 파트의 요미 대사는 **880줄**이다. 히로인과 단둘이 있는 방의 대사가 **25줄**인 게 비정상이다.

### 10.2. 토픽 = 화제가 아니라 **장면(Scene)**

이름은 `TalkTopic` 그대로 두되(세이브 호환), **작성 단위의 정의를 바꾼다.**

| | 지금의 토픽 | **개정 — 장면** |
| --- | --- | --- |
| 정의 | "식사" 같은 **화제 분류** | **시간·장소·요미의 상태가 정해진 한 장면** |
| 예 | `TALK_MEAL_001` = 밥 얘기 | `TALK_MEAL_001` = *새벽 2시. 라면 물을 올려놓고 오빠를 기다리다 식탁에 엎드려 졸고 있다* |
| 노드 | 2~4 | **4~8 (권장 6)** |
| 결말 | 마무리 대사 1줄 | 여운. 결론 짓지 않는다 |

**장면이 정해지면 대사는 저절로 늘어난다.** "밥 얘기"에서는 세 마디면 할 말이 끝나지만, "새벽 2시에 졸다 깬 요미"에게는 왜 안 잤는지, 라면이 불었는지, 오빠는 왜 이제 왔는지, 내일은 어쩔 건지가 전부 대사가 된다. **물량 부족은 작가의 문제가 아니라 단위 설정의 문제였다.**

### 10.3. 지문 줄 — 세 번째 화자

라이트 노벨의 대화가 자연스러운 이유의 절반은 **대사 사이의 서술**이다. 지금 채팅 로그에는 그 채널이 없다.

```
요미 ▌…오빠 왔어?
     ▌  눈을 반쯤 뜬 채로 고개만 든다. 냄비에서 김이 다 빠져 있다.     ← 지문
요미 ▌라면... 아까 끓였는데.
요미 ▌지금은 좀 불었을 거야.
```

| 항목 | 규칙 |
| --- | --- |
| 표시 | **말풍선 없음.** 중앙 정렬, 회색(`#8B8B9A`), 이탤릭, 행 높이 축소 |
| 화자 | 없음. 요미도 플레이어도 아니다 |
| 길이 | **40자 이내**, 1~2문장 |
| 빈도 | **토픽당 3~5줄.** 도입에 1, 감정이 바뀌는 지점에 1~2, 마무리에 1 |
| 내용 | **행동과 사물만 적는다.** 감정을 설명하지 않는다 |
| 시점 | 3인칭 현재형 서술. **존댓말·반말 판정 대상이 아니다** (린터에서 분리) |

> ❌ `요미는 서운했다.` ← 감정 설명. 대사가 할 일을 지문이 뺏는다
> ✅ `폰을 뒤집어 놓는다.` ← 행동. 서운한 건 플레이어가 읽어낸다

**구현은 싸다.** `AppendLine`에 이미 `isYomi` / `isSystem` 분기가 있다. `isNarration` 하나를 더한다 (`R-i`).

### 10.4. 호감도 배분 — 노드 단위에서 **토픽 단위**로

노드가 6개로 늘면 기존 규칙(`노드당 +3 정확히 1개`)은 **한 판 최대 +18**을 만든다. 힌트 임계가 4/7이므로 아무렇게나 눌러도 티어 2가 뜬다. 힌트 경제가 붕괴한다.

| | 기존 | **개정** |
| --- | --- | --- |
| 규칙 | 노드당 `+3` 정확히 1개 | **토픽당 `+3` 1~2개.** 나머지 노드의 상한은 `+1~2` |
| 토픽 최대 획득 | 노드 수 × 3 | **12 고정 상한** (현재 최대치와 동일 — 힌트 임계 불변) |
| `+3` 위치 | 아무 데나 | **토픽 후반 절반에만** |

6노드 배분 예: `1 · 1 · 2 · 3 · 2 · 3` = 12

**부수 효과 둘.**
1. 선택지 대부분이 `+0~1`이 되면서 **선택이 점수판에서 성격 표현으로 바뀐다.** 이게 9.1절 `C-3`(정답 암기)의 근본 해결이다.
2. 결정적 대사가 후반에 몰리므로 **중도 이탈 파밍 유인이 더 줄어든다** (`TS1`과 같은 방향).

### 10.6. 작성 지침 — "자연스럽다"를 규칙으로 바꾼 것

**대사를 생성·작성할 때 이 절을 규칙으로 강제한다.** 바이블 3~5절(요미)과 2.2·4.6절(플레이어)이 *누가 말하는가*를 정한다면, 이 절은 *어떻게 흘러가는가*를 정한다.

#### N-1. 장면부터 확정한다

대사를 한 줄도 쓰기 전에 다음을 채운다. **비어 있으면 대사가 공중에 뜬다.**

| 항목 | 예 |
| --- | --- |
| 시간 | 새벽 2시 |
| 장소·상태 | 식탁. 냄비는 불 꺼진 채, 요미는 엎드려 졸고 있었다 |
| 요미가 하려던 것 | 오빠가 올 때까지 기다렸다가 같이 먹기 |
| 어긋난 것 | 오빠가 늦었고 라면이 불었다 |
| 요미가 **말하지 않을** 것 | 몇 시간을 기다렸는지 |

마지막 칸이 중요하다. **캐릭터가 숨기는 것이 있어야 대사에 밀도가 생긴다.**

#### N-2. 감정 곡선 하나를 6노드에 배분한다

| 노드 | 역할 | 호감도 상한 |
| --- | --- | --- |
| 1 | **도입** — 상황 제시. 아직 본론이 아니다 | +1 |
| 2 | **곁길** — 사소한 투정, 딴소리 | +1 |
| 3 | **균열** — 숨기던 게 삐져나온다 | +2 |
| 4 | **직면** — 요미가 진짜 하려던 말 | **+3** |
| 5 | **전환** — 급격히 풀리거나 우쭐해진다 (바이블 3.2절 낙차) | +2 |
| 6 | **착지** — 결론이 아니라 여운 | **+3** |

**3노드로는 이 곡선이 안 그려진다.** 도입-본론-끝밖에 못 담는다. 그게 지금 기계적으로 읽히는 구조적 이유다.

#### N-3. 화제는 직선으로 가지 않는다

6노드 중 **최소 1개는 본론과 무관해도 된다.** 사람은 하려던 말을 한 번에 안 한다.

> `라면 얘기 → (곁길) 오빠 옷에 뭐 묻었어 → 라면 얘기로 복귀`

곁길 노드는 호감도를 거의 주지 않는다(+0~1). **효율이 아니라 질감을 담당한다.**

#### N-4. 모든 대사가 정보를 나르지 않는다

리액션·되묻기·말 겹침을 섞는다. 정보 밀도 100%짜리 대사만 이어지면 **보고서**가 된다.

> `어?` · `...뭐?` · `아니 그게 아니라` · `그건 그렇고` · `...` (침묵 1줄)

**침묵도 한 줄이다.** `...` 만 있는 말풍선, 또는 지문으로 처리한 공백.

#### N-5. 길이를 섞는다

연속 3줄이 전부 20자 이상이면 벽처럼 읽힌다. **짧은 줄 - 짧은 줄 - 긴 줄** 리듬을 기본으로 한다.

> `오빠.` / `왔어?` / `아니 됐어, 어차피 다 불었을 거야. 지금 다시 끓이면 되니까.`

#### N-6. 요미의 낙차를 장면당 최소 1회

바이블 3.2절(위축 → 우쭐)이나 3.5절(차트 인격 전환) 중 하나를 **반드시 한 번** 쓴다. 안 쓰면 그 장면은 다른 캐릭터가 말해도 되는 장면이다.

#### N-7. 마무리는 닫지 않는다

`ClosingLine`은 결론이 아니라 여운이다. 다음에 이어질 여지를 남긴다.

> ❌ `오늘 정말 즐거웠어! 내일도 놀자!` ← 요약이자 종료
> ✅ `...라면, 내일은 안 불게 끓여줄게.` ← 다음이 있다

## 11. 출력 연출 — 말풍선이 쏟아진다

> **발의**: 2026-08-13. 1차 구현 후 **"요미가 채팅을 동시에 여러 개 쏟아내서 차례대로 읽기 불편하다"**
> **요구**: 텍스트가 입력되는 연출로, 적당한 텀을 주며 출력
> **상태**: 기획 확정 대기

### 11.1. 진단 — 0.4초는 텀이 아니다

버스트(R-1)는 넣었지만 **간격을 사람이 읽는 속도가 아니라 임의의 상수로 잡았다.**

| | 현재 동작 | 사람이 실제로 필요한 시간 |
| --- | --- | --- |
| 20자짜리 한 줄이 뜨는 방식 | **통째로 즉시** | — |
| 다음 줄까지 간격 | **0.4초 고정** | 읽는 데 1.5~2초 |
| 3줄 버스트 총 소요 | **0.8초** | 4.5~6초 |

**첫 줄을 읽기 시작하기도 전에 셋째 줄이 도착한다.** "쏟아진다"는 정확한 표현이고, 원인은 두 가지다.

1. **줄이 통째로 등장한다** — 시선이 어디서 시작할지 모른다. 세 덩어리가 동시에 시야에 들어온다
2. **간격이 길이와 무관하다** — 5자짜리 `...어라?` 와 30자짜리 문장이 똑같이 0.4초를 받는다

### 11.2. 설계

| ID | 장치 | 값 |
| --- | --- | --- |
| **D-1** | **타자기 출력** — TMP `maxVisibleCharacters`를 한 글자씩 올린다 | **0.045초/자** (한글 초당 약 22자). 20자 = 0.9초 |
| **D-2** | **문장부호 정지** — 구두점에서 손이 멈춘다 | `,` +0.08 · `.!?` +0.15 · `...` **+0.35** |
| **D-3** | **줄 사이 여운** — 길이에 비례 | `0.25 + 글자수 × 0.012`, 상한 0.8초 |
| **D-4** | **지문은 타자기 제외** | 즉시 표시 + 0.55초. 서술은 대사와 리듬이 달라야 하고, 타이핑까지 하면 늘어진다 |
| **D-5** | **선택지 등장 텀** | 마지막 줄 완료 후 **0.3초**. 지금은 마지막 글자와 동시에 버튼이 튀어나온다 |
| **D-6** | **2단 스킵** | 클릭 1회 = **현재 줄 즉시 완성**, 2회 = 다음 줄로. 현재는 대기 시간만 건너뛴다 |
| **D-7** | **속도 상수 한 블록** | 연출 속도는 실기로 봐야 정해진다. 흩어 두면 못 고친다 |

**`D-2`가 이 개편의 핵심이다.** 요미 대사는 `...`가 압도적으로 많다(위축·머뭇거림). 말줄임에서 0.35초 멈추는 것만으로 **"머뭇거리다 말한다"가 연출로 읽힌다.** 대사를 한 줄도 안 고치고 캐릭터가 드러난다.

**체감 계산** — 3줄 노드(각 20자 · 말줄임 1개)

| | 현재 | 개편 후 |
| --- | --- | --- |
| 1줄 | 0초 (즉시) | 0.9 + 0.35(말줄임) = 1.25초 |
| 줄 사이 | 0.4초 | 0.49초 |

## 12. 플레이어 대사가 설정을 안 따른다

> **발의**: 2026-08-13. **"바이블에 플레이어 설정도 기술돼 있는데, 플레이어 대사가 그 설정의 말투와 분위기를 못 따라가고 있다"**
> **상태**: 기획 확정 대기

### 12.1. 감사 — 선택지 100개 실측

바이블 2.2절은 플레이어를 **5축**으로 정의한다. 실제 데이터에 그 축들이 어떻게 나타나는지 셌다.

| 축 (바이블 2.2절) | 선택지 수 | 비중 |
| --- | --- | --- |
| **무던함** (짧게 받는다, 리액션) | 약 75 | **75%** |
| **속정** (걱정을 행동·조건으로) | 약 11 | 11% |
| **책임감** (자기 몫으로 가져온다) | 약 5 | 5% |
| **우유부단** (끊지 못하고 끌려간다) | 약 4 | 4% |
| **감춘 불안** (자기 불안이 새어 나온다) | **0** | **0%** |

**무던함은 기본값이지 전부가 아니다.** 지금은 사실상 1축 캐릭터고, 바이블이 "핵심"이라고 못 박은 **우유부단이 4%**, **감춘 불안이 0건**이다.

> 참고로 처음 의심했던 *"되묻기만 한다"* 는 **틀렸다.** 물음표로 끝나는 선택지는 100개 중 10개(10%)뿐이다. 문제는 문장 형태가 아니라 **축의 편중**이다.

**+0 정의 위반** — 바이블 2.2절은 `+0 = 회피·얼버무림, 냉담도 조롱도 아님`으로 못 박았다.

| 위치 | 대사 | 문제 |
| --- | --- | --- |
| `TALK_MEAL_001` 직면 | `돈은 내가 벌잖아.` | ⚠️ **명백한 위반.** 얹혀사는 요미가 부채감을 고백하는 **바로 그 순간**에 경제적 우위를 들이민다. 2.2절 4번(남의 아픔을 함부로 비웃지 않는다) 정면 위반 |
| `TALK_ANGER_001` 곁길 | `혼잣말 잘 들리네.` | 삐진 상대에게 되받는 비꼼. 4.6절 금지 1번 |
| `TALK_SLEEP_001` 곁길 | `익숙해질 거야.` | 불안을 가볍게 넘긴다. 경계선 |
| `TALK_LOVE_001` 도입 | `네 목소리는 원래 커.` | 허용 범위지만 애정 장면 도입에서 톤이 튄다 |

### 12.2. 구조적 원인 — 선택지에 **응답**만 있고 **발화**가 없다

이게 근본이다. 축 편중은 결과일 뿐이다.

**요미의 대사 77줄이 전부 질문이거나 토로다.** 그러면 플레이어에게 남는 자리는 **응답 하나뿐**이다. 응답만 하는 사람은 무던해 보일 수밖에 없고, 자기 불안을 흘릴 자리가 애초에 없다.

```
지금:   요미가 말한다 → 플레이어가 받는다 → 요미가 말한다 → …
        플레이어가 자기 얘기를 꺼낼 지점이 6노드 중 0곳
```

**따라서 플레이어 선택지만 고쳐서는 해결되지 않는다.** 요미 대사에도 손이 간다 — **요미가 오빠에게 묻는 노드**를 만들어야 한다.

> `오빠는 오늘 어땠어?` 한 줄이면 그 노드의 선택지 3개가 전부 **플레이어의 자기 발화**가 된다. 감춘 불안(2.2절 5번)이 나올 수 있는 유일한 자리다.

#### P-1. 축 태그

```csharp
/// <summary>플레이어 성격 5축 (바이블 2.2절). 어느 축을 쓰는지 데이터에 남긴다.</summary>
public enum TalkTrait
{
    Plain,    // 무던함 — 기본값. 짧게 받는다
    Warm,     // 속정 — 걱정을 행동·조건으로 돌려 말한다
    Duty,     // 책임감 — 문제를 자기 몫으로 가져온다
    Anxious,  // 감춘 불안 — 자기 불안이 말줄임으로 샌다
    Waver,    // 우유부단 — 끊지 못하고 끌려간다
}

public TalkChoice(string text, TalkTrait trait, int affection, string reply = null)
```

**선택 인자가 아니라 필수로 둔다.** 기본값을 주면 전부 `Plain`이 되어 지금 상태가 그대로 굳는다. 100개를 고쳐야 하지만 `P-3`/`P-4`로 어차피 재작성 구간이 겹친다.

#### P-5. 노드 역할 × 플레이어 축

| 노드 | 요미 | **플레이어 권장 축** |
| --- | --- | --- |
| 도입 | 상황 제시 | `Plain` — 짧게 받는다 |
| 곁길 | 딴소리 | `Plain` · **`Waver`** — 끌려가준다 |
| 균열 | 숨긴 게 샌다 | `Warm` — 캐묻지 않고 곁을 준다 |
| **직면** | 진짜 하려던 말 | `Duty` · **`Anxious`** — **여기서만 자기를 연다** |
| 전환 | 급히 밝아짐 | `Plain` · `Waver` — 맞춰준다 |
| 착지 | 여운 | `Warm` · `Duty` |

**직면 노드가 유일하게 플레이어가 자기를 여는 자리다.** 지금은 직면 22개 중 자기 발화가 `네가 없으면 너무 조용해.` 하나뿐이라, 상호 개방이 아니라 **상담**처럼 읽힌다.
